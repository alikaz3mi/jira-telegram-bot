# Changelog — v2.42.0

## Summary

The assistant can now answer questions about work that is not the asker's
own, and the daily reminder became a conversation instead of an
interrogation.

Every tool the assistant had ran `assignee = <caller>`. That made a whole
class of ordinary question unanswerable — "which epics are in this sprint?",
"what design work is defined?" — and the model, given only a personal task
list, answered them anyway with whatever it had. Asked what design work was
in ParsChat's sprint, it listed the caller's own backend stories and called
them design; asked what was planned for Instagram, it listed every epic in
the sprint. The fix is not a better prompt; it is tools that query the
project rather than the person, and that can report finding nothing.

The reminder used to ask about up to twelve tasks one at a time, twenty-five
messages before anyone had said anything. It now opens with a digest — what
became unblocked, what regressed, what the sprint is for — and one open
question. What the person writes is parsed into worklogs, and only the tasks
their report did not cover are asked about individually.

## Features

### Team-wide sprint questions
- `sprint_epics` reports which epics a project's open sprint advances, by
  rolling its stories up to their parents. Epics carry no assignee, so they
  were unreachable by every existing tool: ten existed in Kheradyar while the
  assistant reported none.
- `sprint_board` lists a project's sprint for the whole team, filtered by
  unit, person or issue type. Because these issues carry no Jira component or
  label, «طراحی» resolves through each person's recorded unit in
  `user_components` — the only record of who does design.
- A filter that cannot be applied is refused, never dropped. An unknown unit
  says so and names the ones it knows; a unit nobody is recorded in says
  that too. Silently answering the unfiltered question is what produced the
  original wrong answer.
- `sprint_board` also takes a **topic**, matched by meaning rather than by
  keyword. Asked what was planned for Instagram, the assistant previously
  listed all six epics in the sprint — four of them unrelated — because no
  tool could filter by subject. A keyword filter would have been little
  better: it finds only the issues that spell the word out, missing
  «ویترین» and «کامنت» that are plainly the same work.
- Authorisation for project-wide reads is decided in Python: a role that may
  read others always may, and everyone else must have work of their own in
  that project.

### Briefings
- `my_briefing` answers "what should I do?" as an overview per project rather
  than one flat list. Asked without naming a product, it previously picked the
  single busiest one and listed issue keys under it — somebody carrying work
  in three products got one product's list and no sign the rest existed.
- Inside each project the work is framed by the **releases it ships in**: the
  release with the nearest delivery date, how many of the person's open tasks
  ride on it, and how many releases their work spans in total. A release
  carries a date; a task usually does not, so this is where a deadline was
  visible all along and never surfaced.
- The tasks due soonest are ranked by **Target end**, and an absent date never
  sorts ahead of a real one. A project where nobody sets dates falls back to
  sprint commitments rather than rendering an empty section.
- Dates are spoken in **Jalali** — «۲۴ شهریور», not `2026-09-15`. Sprints are
  named for Jalali half-months and the team plans in them; a date the reader
  has to convert is a date they misread. `releases` gained the same treatment,
  including the start date beside it, which had stayed Gregorian.
- A briefing can be about **someone else**. "تسک‌های خانوم لطفیان چیه؟"
  previously fell through to a bare list, because the release framing was
  only reachable for the caller. The person is resolved and authorised in
  Python by the same check every other tool uses.
- Names are spelled the way the directory spells them, not the way they were
  typed. Echoing «خانوم لطفیان» back when the record says «خانم لطفیان» reads
  as carelessness about the person being described. The spelling comes from
  the resolution already performed — re-resolving a Jira username through a
  fuzzy alias search could land on a different person.
- `within_days` answers "این هفته" and "امروز". The window narrows what is
  **listed** and never what is **counted**, and the heading names the window
  («مهلت‌های ۷ روز آینده (۲ مورد)»). A filtered list headed "due soonest" is
  how four tasks came to stand in for twenty-nine.
- `due_within_days` is gone from `list_tasks`. Prompt wording could not keep
  the model away from it: it was an exact literal match for "این هفته", so
  the model reached for the raw list and the briefing never ran. Removing the
  parameter removes the choice.
- Each task renders as a **linked title above its own detail line**, rather
  than a numbered line led by an issue key. Nobody recognises their work by
  `KHERADYAR-37`, so the summary carries the link and the key moves down
  beside the status and the date. Status carries a colour, and each block
  carries an icon (📁 project, 🚀 release, ⏰ deadlines, 🔗 the rest).
- **Markdown links are converted to anchors**, not stripped. The model was
  rewriting `<a href="…">title</a>` into `[title](url)` even though the
  prompt already told it not to — which is the proof that prompt wording is
  the wrong layer for this. The reply goes out as HTML, so the rewrite put a
  raw URL on screen and took the link away entirely.
- A URL the model **repeats beside its own link** is removed. A Jira search
  URL is two hundred characters of percent-encoded JQL, and duplicated it
  wrapped across four lines of the reply with no way to tell it was the link
  the reader already had. Only a duplicate of an anchor already present is
  removed, so a link offered on its own still reaches the user.
- `list_tasks` renders a task the same way `my_briefing` does. The two had
  drifted: the same task looked like a linked title in one answer and a bare
  issue key in the other, depending on which question found it. The
  rendering lives in one place now.
- Markdown emphasis is stripped from the model's answer before it is sent.
  The reply goes out as HTML, so a model that decorated its relay with
  `**Kheradyar**` put literal asterisks on screen. Instructing it not to is
  unreliable — the formatting is a habit, not a decision — so the markers
  come off in Python, where the guarantee holds. A lone `*` is left alone.
- Summaries, release names and project names are **HTML-escaped**. A Jira
  summary containing `&` or `<` previously made Telegram reject the entire
  message, losing the whole briefing rather than one character.
- Screenshots on an urgent bug are downloaded and sent as real images.
  Attachments were previously rendered as links to authenticated Jira URLs,
  which nobody can open from a phone.

### Releases
- A new `releases` tool reads Jira versions: what is due to ship, when, and
  what is still open against it. "When does Instagram get verified?" was
  unanswerable before — the date sat on a version in the project the whole
  time while the assistant searched sprint contents and reported finding
  nothing.
- `task_details` names the release a task ships in. The whole version read is
  guarded, not just the fetch: losing a task's description because a version
  field was malformed is not a trade worth making for a nice-to-have line.
- `topic` narrows releases by meaning, so the release search answers the same
  subject questions the sprint board does.

### Ambiguity is a question, not a refusal
- A tie between **plausible** issues now becomes a question with tappable
  options instead of a refusal. Reported: "for explaining the tasks to
  parschat's team, 4 hours" scored 0.496 against its best candidate and led
  the runner-up by 0.055, so the margin gate reported no match — work that
  had really been done went unrecorded and the user was told to type an
  issue key by hand. The gate was treating "several things fit" and "nothing
  fits" as the same answer.
- A tie between **weak** rows is still refused. What separates the two cases
  is how good the leader is (`ambiguous_similarity`, 0.42), not how close
  the race was. Only candidates within 0.06 of the leader join the question,
  capped at four — padding the options makes the choice harder, not easier.
- **A high score no longer settles a split on its own.** `_STRONG_MATCH`
  (0.45) previously auto-resolved the leader even when the runner-up was
  0.44, silently writing real hours to the wrong task; it now also requires
  a clear lead. This was the more dangerous half of the bug: a worklog on
  the wrong issue is painful to unwind, while a question costs one tap.
- The question **explains itself**: how many issues matched, which project
  they are in, and that the ranking could not choose between them. Button
  labels lead with the summary rather than the issue key, since that is what
  somebody recognises their own work by.

### Reading which project a report is about
- **A team named as the audience of the work is no longer read as the
  project.** "توی برد خودم ینی علی کاظمی ... یکی روی تسک توضیح وظایف به تیم
  پارسچت" narrowed to PARSCHAT's 24 issues, because the scanner found
  «پارسچت» in the *description of the work* and preferred it for being the
  longest match — while the same sentence said the tasks were on the
  caller's own board. AK-13, the issue meant, was never shown to the model.
  A name after «به تیم» / "for the … team" is now skipped, and among real
  candidates the one named **first** wins, since the board is stated before
  the work is described.
- A short project key like `AK` counts when it stands as a whole word. The
  scanner ignored anything under three characters to avoid matching inside
  ordinary words, which also made a two-letter project unnameable.
- **Ranking now runs against the same list the model chose from.** The model
  saw 24 narrowed candidates while the reranker ranked against all 30, so a
  single report drew one split from the narrowed list and the next from the
  full one — which is how one sentence produced a PARSCHAT issue and an AK
  issue side by side.
- A correction keeps the hours it corrects. "تسک اول رو اشتباه تشخیص دادی،
  AK-13 بود" was answered with "بگویید چند ساعت و روی چه کاری" — asking
  again for hours the user had already stated twice. An issue key the user
  types now also settles the match outright, ahead of any similarity score.
- Fixed a corrupted rule in `parse_worklog_report.yaml`: rule 4's sentence
  had been split in half with two paragraphs wedged inside it, and two rules
  were both numbered 4.

### A second tap is not an error
- Confirming a report **removes its buttons before the first write**. Writing
  two worklogs took thirteen seconds, during which the keyboard stayed on
  screen and looked unresponsive; a second tap then found the report already
  consumed and answered "خطا رخ داد". Both worklogs were in Jira by then, so
  the message said the opposite of what had happened — and invited logging
  the same hours a second time.
- A confirmation or a choice arriving after the report is gone now answers
  "این گزارش قبلاً ثبت شده است" as a toast, leaving the result message
  intact. Nothing is written twice.
- A missing user config no longer discards the parsed report. It was popped
  before the config was read, so a config miss threw away the parse and the
  user had to describe their day again.

### Similarity ranking for worklogs
- Issue matching now ranks candidates by embedding similarity
  (`text-embedding-3-small`, 512 dimensions, renormalised after truncation).
  Measured on this team's own issues, 512 matched full-size retrieval exactly
  at a third of the storage.
- A **margin gate** decides whether anything matched at all. Absolute
  similarity cannot: nonsense scored 0.386 here while a genuine near-miss
  scored 0.375. Real matches lead the runner-up by 0.15–0.27; non-matches by
  0.02–0.04.
- Ranking runs per split, on the description the model extracted, not on the
  whole message. «دیروز ۲ ساعت ریموت روی تنزل خودکار کار کردم» embeds hours,
  a date and a way of working alongside the task; the right issue still led,
  but by 0.04, and the gate then read it as no match.
- Topic search uses a **higher floor (0.38)** than worklog matching, and a
  floor rather than a margin. A worklog names one issue; a topic spans a
  whole epic, so a margin over the runner-up is the wrong test. Measured on
  this sprint: every true Instagram match scored ≥ 0.400 while a subject the
  project has never heard of still peaked at 0.349 — shared Persian
  vocabulary alone carries a query that far. The first attempt used the
  worklog floor and returned 18 Instagram items and 25 for a topic that does
  not exist here.
- Vectors are cached on disk by content hash, so an unchanged summary is
  never paid for twice and an edited one is a miss without explicit
  invalidation.

### Daily digest
- The reminder opens with one message: blockers that cleared, tasks that
  regressed, work in flight, and the backlog counted rather than listed.
- The reply is free text, parsed by the same worklog pipeline. A report that
  covers everything ends the check-in; anything it missed is asked about
  one at a time, capped at eight.
- `/tasks` walks through tasks individually for anyone who prefers it.
- Every task keyboard now offers «بقیه را بعداً», which ends the queue.
  Previously a check-in could only be finished or abandoned.

## Fixes

- **Blocking links were read in both directions.** Jira puts what an issue
  waits on in `inwardIssue` and what it holds up in `outwardIssue`; the parser
  took whichever was present, so a task that blocked three others was read as
  depending on them. Correcting it found six tasks with real dependencies
  where four were seen before — and surfaced that RETARGET-9 has been sitting
  in Backlog with its only blocker already done.
- **A stated project was parsed and then ignored.** "برای پارسچت ۴ ساعت"
  produced `project_hint` that nothing read, so a report could be offered two
  buttons from a different project while twenty real ParsChat issues sat in
  the candidate list unoffered. The named project now narrows what the model
  is shown, before it chooses — filtering its answer afterwards is too late,
  because a shortlist of entirely out-of-project rows leaves nothing to keep.
- **Finished work was presented as outstanding.** `Cancel` sits in Jira's
  `Done` category without setting a resolution, so `resolution = Unresolved`
  still returned it. Eight completed tasks were queued for one person's daily
  check-in, and two cancelled bugs were announced as urgent.
- **The assistant could hang indefinitely.** `agent.ainvoke` had no timeout,
  so a tool loop that did not converge left the user watching "در حال
  بررسی…" forever. Capped at 90 seconds and failing visibly.
- **A corrupted byte replaced the link emoji** in the task reminder, printing
  `�` on every message.
- **`اسپرینت: N/A`** was printed on every task without a sprint, which is most
  of them. The line now appears only when there is a sprint to name.
- A sprint story with no epic is reported separately rather than dropped, so
  the epic totals cannot be misread as the whole sprint.

## Notes

- **The unit map is incomplete.** Only 9 of 27 people have a recorded unit on
  PARSCHAT, and nobody is recorded as Backend — so «بک‌اند» correctly answers
  that nobody is registered rather than guessing, but answers nothing useful.
  `sprint_board`'s unit filter is only as good as `user_components`.
- **The daily reminder is still gated to a single user** by a hardcoded
  `telegram_username != "alikaz3mi"` check. Nothing reaches the team until
  that is removed deliberately.
- **"Recently unblocked" uses `updated`, not `resolutiondate`**, because the
  latter is empty on workflows that reach Done without a resolution. An edit
  therefore counts as a change; it errs towards mentioning a cleared blocker
  rather than staying silent about one.
- Embedding ranking improves which issues are offered, not recall of work
  that was never filed. A description matching nothing scores low at every
  dimension, and is reported as no match rather than guessed at.

## Dependencies

None added. Cosine similarity is computed in plain Python, and the embedding
client is the `openai` package already present.
