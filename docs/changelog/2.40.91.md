# Changelog — v2.40.91

## Fixes

### Critical: `NameError` crash in multi-assignee Story creation
- **Problem:** `create_developer_board_task_from_feature` passed an undefined
  variable `sprint_info` to `_create_subtasks_for_assignees`. This crashed with
  `NameError` every time a feature had multiple assignees (task_type="Story"),
  preventing all multi-assignee Story+subtask creation from working.
- **Root cause:** The local variable holding the sprint dict was named `sprint`
  (returned by `_find_best_sprint_from_list`), but the call site passed
  `sprint_info` (never defined).
- **Fix:** Changed the call to pass `sprint` instead of `sprint_info`.
  Updated `_create_subtasks_for_assignees` signature from
  `sprint_info: SprintInfo` to `sprint: Optional[Dict[str, Any]]` since the
  parameter was unused in the method body.

### High: Duplicate epics created due to missing `summaries_match` post-filter
- **Problem:** `_create_epic_if_not_exists` in both `SynthPMRepository` and
  `JiraOperationsMixin` used `summary ~ "..."` JQL (Lucene full-text) but
  did **not** post-filter results with `summaries_match`. This violated the
  v2.40.89 fix intent and allowed Lucene false positives to either:
  - Link tasks to the wrong epic (when a similarly-named epic existed), or
  - Create duplicate epics (when no false positive happened to be returned first).
- **Fix:** Both methods now fetch up to 20 results (`max_results=20`), post-filter
  with `summaries_match`, and only create a new epic when no exact match is found.

### Medium: `_find_best_sprint_from_list` could return closed sprints
- **Problem:** When no active or future sprint was found, the fallback path returned
  a closed sprint from `_get_or_create_sprint_cached` without checking its state.
  While callers handled this, it caused unnecessary warnings and wasted API calls.
- **Fix:** Fallback now checks `sprint.get("state") == "closed"` and returns `None`
  instead of a closed sprint.

### Medium: Worklog author lost during task-to-subtask recreation
- **Problem:** `_migrate_worklogs` in `JiraServerRepository` used
  `jira.add_worklog()` which always attributes worklogs to the API user.
  When tasks were recreated as subtasks (the fallback conversion path),
  all worklogs appeared as logged by the bot instead of the original authors.
- **Fix:** New `_add_worklog_via_rest` method tries the Jira REST API
  (`POST /rest/api/2/issue/{key}/worklog`) with the original `author` field.
  Falls back to `jira.add_worklog()` if the REST call fails (e.g. insufficient
  permissions). On Jira Server with admin rights, this preserves the original
  worklog author.

### Low: Reporter not preserved during subtask recreation
- **Problem:** `_build_subtask_fields_from_issue` copied assignee, components,
  labels, dates, and priority but **not** the reporter. Recreated subtasks got
  the API user as reporter.
- **Fix:** Added reporter field to the copy list.

## Tests

### Fixed 5 pre-existing test failures in `test_synth_pm_release_workflow`
- **Root cause:** The v2.40.90 change introduced `validate_feature_for_update`
  for existing tasks, but tests only mocked `validate_feature_for_task_creation`.
  Features with `developer_board_issue_key` tried calling the unmocked
  `validate_feature_for_update` on a `MagicMock`, causing unpacking errors.
- **Fix:** Added `validate_feature_for_update = MagicMock(return_value=(True, None))`
  to both test class `setUp` methods.
